# Проверка регрессий скорости сайта

[Ролик, 00:07–00:14 и 01:17–01:21](https://www.youtube.com/watch?v=XeCssI7RSb0) · [Lighthouse](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring) · [Web Vitals](https://web.dev/articles/vitals)

Разведка извлекла рекомендации по дедупликации запросов, паузе перед поиском, пагинации и проверкам на медленных устройствах. Совет предложил сначала добавить воспроизводимое измерение и применять оптимизации по обнаруженному узкому месту.

Тестировщик сравнивает два навигационных отчёта Lighthouse на одном маршруте, версии и профиле замера. Замерять на одной машине с одинаковым режимом кэша. Допуски для шумных измерений согласовать до изменения. Команда из корня NFAI:

```bash
python3 projects/03-telegram-tooling/work/check_performance.py baseline.json candidate.json
```

По умолчанию допустимое ухудшение равно нулю. При заранее заданном допуске передайте `--allow-time-ms` для LCP и TBT и `--allow-cls` для CLS. Выход 0 означает отсутствие ухудшения сверх допуска, 1 означает регрессию, 2 означает несопоставимые или неполные отчёты. TBT здесь лабораторная метрика. При наличии полевых данных INP оценивают отдельно.

Проверено на шести синтетических отчётах: улучшение, регрессия, согласованный допуск, другой профиль, отсутствующая метрика и нечисловое значение. Для живого прогона Lighthouse 13.6.0 попытался запустить Chromium на локальной тестовой странице. В этой среде Chromium получил запрет при открытии сокета. Полевых и лабораторных выводов о реальном сайте пока нет.

После повторного ревью Совета добавлена проверка конечного адреса и режима отчёта. Проверено на совместимых превью, переадресации на другую страницу того же сайта, переадресации на другой хост, пропущенном конечном URL и отчёте snapshot.
